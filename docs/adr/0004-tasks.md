# 0004. Tasks

Status: accepted (2026-10-15). Builds on [0001](0001-electric-tanstack-db-sync.md) and [0003](0003-projects-and-columns.md): tasks are a synced shape scoped by membership, ordered like Columns, and ticket ids use the Project key.

## Context

Projects and Columns had nothing to hold. Kaneo, which Morrow started from and now only references, has tasks, but its model does not fit Morrow's sync design:

- A task stores its state twice (a status slug and a column id), "done" is computed three ways, and "planned" and "archived" are fake statuses that throw away the task's column.
- Order is a dense integer, so one drag rewrites a column and needs a full-board snapshot to detect conflicts. The whole board, descriptions included, is loaded page by page.
- Small edits go through a full-replace PUT that can revert other people's changes. Side effects run after commit and are lost on a crash.
- Import drops labels, expects internal user ids while its dialog shows an email, runs one transaction per task with no limits and never shows its warnings.

## Decision

**A Task belongs to one Project and sits in one Column.** Its state is that Column's category; there is no status field. It has a ticket id built from the Project key and a per-Project number (`MOR-12`), a title (1–500 characters), a markdown description (up to 100,000), a priority (`none`, `low`, `medium`, `high`, `urgent`), one optional assignee, an optional due date, a fractional-index `position`, `completedAt`, `archivedAt`, `createdBy` and timestamps. There is no `workspaceId` column; the Workspace comes through the Project.

**Ticket numbers** come from `project.last_task_number`, incremented in the write transaction with the Project row locked (`lockProject`). The same lock serialises every task write of a Project and refuses writes to an archived Project. Numbers are never reused. Renaming a Project key renames every ticket id; old ids stop resolving, as ADR 0003 accepts.

**`completedAt` is derived from the Column category and stored.** Every write that changes `columnId` sets it to now when the new Column is `done` or `canceled` and the old one was not, clears it when the task leaves those categories, and keeps it between two closed Columns. The same rule runs when a Column changes category (all its tasks) and when a Column is deleted (its tasks move to the target Column, appended after the target's last position in their existing order, with `generateNKeysBetween`). The rule is one function, `nextCompletedAt`, in `@morrow/sync-schemas`.

**`archivedAt` keeps the Column and the position**, so unarchiving puts a task back exactly where it was. Archived tasks stay editable. Archiving is a task-level write, not a status.

**Order** is the same fractional-index key as Projects and Columns (`text COLLATE "C"`, unique on `(column_id, position)`, generated by the client, validated by the server, `POSITION_TAKEN` on a collision, sorted in JavaScript). One drag writes one row.

**Foreign keys.** `project_id` cascades. `column_id` is `NO ACTION`, not `SET NULL`: Column delete moves its tasks first, and `NO ACTION` (checked at the end of the statement, unlike `RESTRICT`) lets a Project delete cascade to its Columns and tasks in one statement. `assignee_id` and `created_by` are `SET NULL`.

**Assignment.** The assignee must be a current Member. Setting yourself, or clearing it when it is you, needs only `task: update` (`create` on create); any other change needs `task: assign`. Removing a Member clears their assignments *in the same transaction as the removal*. Better Auth performs member removal, so no Morrow code runs in that transaction; a `BEFORE DELETE` trigger on `workspace_member` does it. This also covers admin removal and leaving.

**Permissions.** A `task` resource with `create`, `update`, `delete` and `assign`. Viewers have none, Members create and update, Admins and Owners all four. `update` covers every field, Column moves, position, archive and unarchive, and duplicate (which also needs `create`). The migration adds the grants to the default Member and Admin roles of existing Workspaces; custom roles are not touched.

**Sync: one shape, one on-demand collection.** The `tasks` shape covers every task of every Workspace the user belongs to, archived included, through a membership subquery. The web app reads it through one TanStack DB collection in `syncMode: "on-demand"`: each live query's `where` becomes a subset request, so the board loads one Project's unarchived tasks, a done group loads when expanded, and the Archived group loads when expanded. The owner wants a future all-tasks page on the same collection. Every task change in the user's Workspaces still travels on the change stream (`log=changes_only`), so bandwidth scales with how often tasks change, not with how many there are.

**Spike result (2026-10-15).** Before building, a throwaway prototype ran the real stack (Electric behind the real shape proxy, `@tanstack/electric-db-collection` 0.5.9) and showed: (1) a live query with `where projectId = X` sends `subset__where="project_id" = $1` and loads only that Project's tasks; (2) the proxy already forwards `subset__*` (they are Electric protocol parameters) and Electric ANDs the subset with the shape's membership filter, so a subset for another Workspace's Project returns nothing; (3) `awaitTxId` resolves for writes under `changes_only`, for inserts, updates and deletes; (4) inserts into other Projects arrive through the change stream and sit in the collection but never show in the open Project's query, and another user's task never arrives; (5) `cleanup()` empties the collection. One consequence: `collection.preload()` is a no-op for an on-demand collection, so route loaders preload a live query collection instead. The fallback, one eager shape per Project with declared parameters, was not needed.

**Writes** are Procedures in `withTxid` that return `{ …, txid }`. An edit is split into field groups, one Procedure each (title, description, priority, due date, assignee, move, archive, unarchive), so two people editing different fields never overwrite each other. Create takes a client-chosen cuid2 id, Column and position, so the card appears before the server answers; the ticket number exists only after the reply. The server validates the id's format and a collision is a typed error. Description autosave is a debounced paced mutation, last write wins; there is no collaborative editing. Writes bump `updated_at`, so even a no-op write reaches sync and `awaitTxId` resolves.

**Activity.** `task.created`, `task.completed` (entered a `done` Column), `task.canceled` (entered a `canceled` Column) and `task.deleted`, recorded in the write transaction, with the ticket id and title. Field edits, reorders, reopening, archive and unarchive are not recorded.

**Import and export.** Export is a JSON document of the Project's Columns (name, category) and tasks (number, title, description, Column name, category, priority, due date, assignee email, completion, archive and creation times) in board order. Import needs `task: create` and is one transaction: at most 5,000 tasks and 5 MB (the RPC body bound is raised for that one route), Columns matched by name, then category, then the first `unstarted` Column, assignees matched to Members by email, tasks given new consecutive numbers in the file's numbering order and appended per Column in file order. Whatever could not be matched is returned as warnings, not an error; a member without `assign` keeps only their own assignments. A failing row rolls everything back.

**Server-side reads.** `tasks.list` is one Procedure that reads the table, a deliberate exception to "a Shape or a query, never both", for the same reason as `projects.list`: MCP (`list_tasks`) and the account export run on the server. The web app never calls it.

**Project deletion** no longer requires archiving first (revises ADR 0003). The web app asks for the key to be typed; the cascade removes Columns and tasks.

## Compared with Kaneo

One state source (the Column category) and a real `completedAt`; fractional positions (one row per move); per-field Procedures instead of a full-replace PUT; activity written in the transaction; archive that keeps the Column; atomic, bounded import that matches by email and shows warnings; one Procedure for "archive all completed" instead of N calls; on-demand loading instead of the whole board.

## Not now

Bulk selection, labels, comments, attachments, subtasks and relations, start dates and time tracking, reminders, multiple assignees, moving a task between Projects, an all-tasks or my-tasks page (the collection is built for it), calendar and Gantt layouts, virtualised lanes, importers from other tools, MCP write tools, templates and custom fields, collaborative description editing.

## Consequences

- The board is live in every tab and loads only what it shows.
- Timestamps are `timestamp` without time zone in UTC like every other Morrow table, not `timestamptz`; due dates are `date` strings and never pass through `Date`.
- The `tasks` shape is the eighth long-poll on a Workspace page: fine behind HTTP/2 (dev Caddy, prod Traefik, the e2e Caddyfile), and it would stall on plain HTTP/1.1.
- A `workspace_member` trigger owns assignment cleanup; anything that deletes membership rows is covered, and the behaviour lives in a migration, not in the application code.
- Existing custom roles do not get `task` grants; an admin edits them in the roles page.
